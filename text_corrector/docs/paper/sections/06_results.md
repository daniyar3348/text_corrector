# Results and Analysis

We evaluate the system along five axes: (i) error-detection quality against a lexicon heuristic; (ii) end-to-end sentence-level correction against a non-learned baseline and an oracle ceiling; (iii) a per-error-type decomposition of the corrector under oracle detection; (iv) qualitative behaviour; and (v) efficiency and deployment. All results are reported on the held-out test split (25,000 sentence pairs), with detection and end-to-end figures measured on an 8,000-sentence subset. The errors are synthetically injected according to the six-operation error model of Section 4, so the figures characterise behaviour on a programmatically generated rather than human-typed error distribution (see the limitations discussion below).

## Detection Results

The KazRoBERTa token-classification detector attains a token-level $F_1$ of 97.3% (precision 97.1%, recall 97.4%) on the test subset, with 327 false positives. As a non-learned reference point we evaluate a lexicon heuristic that flags any whitespace token absent from the corrector lexicon; this baseline reaches $F_1 = 86.3\%$ but produces 1,818 false positives — roughly $5.6\times$ the number raised by the trained detector. These figures are summarised in the detection rows of Table (detection).

The eleven-point $F_1$ gap, and especially the order-of-magnitude reduction in false positives, illustrates why a contextual encoder is preferable to a membership test. The heuristic cannot distinguish a genuinely misspelled token from a valid but low-frequency or out-of-vocabulary form (a rare proper noun, a neologism, or a legitimately inflected surface form), so it over-flags. The fine-tuned detector, building on the masked-language-model pretraining of KazRoBERTa [liu2019roberta; sagyndyk2025kazroberta] and byte-level subword tokenization for agglutinative Kazakh [sennrich2016bpe], conditions each token decision on sentential context and thereby suppresses the spurious flags that dominate the heuristic's error budget — consistent with the long-standing observation that dictionary-lookup detection is limited and that context is needed to separate true errors from rare valid words [kukich1992techniques].

## End-to-End Correction

At the sentence level — measuring the fraction of test sentences that are *fully* corrected, i.e. that exactly match the reference after correction — the full pipeline corrects 80.5% of sentences. The non-learned baseline (lexicon-heuristic detection followed by the same corrector) reaches 64.6%, while an oracle configuration in which detection is perfect by construction (detection $F_1 = 100\%$) attains 83.5%. These results appear in the end-to-end rows of Table (detection).

Two observations follow. First, replacing the heuristic detector with the trained detector improves full-sentence correction by 15.9 points (64.6% $\rightarrow$ 80.5%), confirming that detection quality is the dominant lever once the corrector is held fixed. Second, the trained pipeline sits within 3.0 points of the 83.5% oracle ceiling. Because the oracle differs from the trained pipeline only in receiving perfect KEEP/ERROR labels, this small residual is precisely the cost of the detector's remaining recall and precision shortfall. The interpretation is that, for this error model, *detection is essentially solved*: even a perfect detector would lift end-to-end accuracy by at most three points. The remaining 16.5 points separating the oracle from a hypothetical perfect system are attributable to the corrector — the corrector, not the detector, is the binding constraint on overall quality. This motivates the per-error-type analysis below, which isolates corrector behaviour under oracle detection.

## Per-Error-Type Corrector Analysis (Oracle)

Under oracle detection the corrector fixes 88.0% of flagged words with a precision-of-changes of 91.6%. Disaggregating by error type reveals a strongly bimodal profile (Table (per-error-type)): the corrector is near-perfect on the substitution-based classes — ka2ru 97.6% and vowel-harmony 97.9% — strong on character duplication (dup) at 93.0% and character swap at 83.0%, but markedly weaker on character substitution (sub) at 70.0% and character drop (deletion) at 62.0%.

The pattern follows from the corrector's candidate-generation mechanism and the information content of each corruption. The ka2ru and harmony classes are deterministic, *reversible* character-level substitutions over a small confusion set (the ka2ru look-alike map $\{ \text{ә→а}, \text{ө→о}, \text{ұ→у}, \text{ү→у}, \text{қ→к}, \text{ғ→г}, \text{ң→н}, \text{і→и}, \text{һ→х} \}$ and the harmony vowel pairs). No surface information is destroyed: every corrupted character still corresponds to its correct counterpart, so the inverse-substitution generator, filtered by lexicon membership, recovers the intended word almost without ambiguity. Duplication is similarly low-entropy — a repeated character is locally redundant and easily removed by the edit-distance fallback (Optimal String Alignment, a restricted Damerau–Levenshtein metric with unit transposition cost [damerau1964technique; levenshtein1966binary]). A swap (transposition) is by construction a single OSA operation and so remains within reach, though its 83.0% rate already shows the corrector struggling when more than one valid lexicon form lies within the search radius.

Drop and sub are the hardest because each *destroys* information that the corrector cannot recover from form alone. A deletion removes a character outright: the corrupted token is shorter, and multiple distinct lexicon entries may be equidistant from it, so the frequency tie-break must guess among genuinely competing reconstructions. A substitution replaces a character with an arbitrary other letter rather than a predictable look-alike, breaking the inverse-substitution path entirely and pushing every such case into the generic edit-distance search, where — as with drop — several plausible candidates often coexist. Crucially, the corrector ranks candidates by lexicon frequency, not by sentential plausibility: it has no contextual or language-model re-ranking stage. When the surface form alone underdetermines the answer, frequency is a weak proxy and accuracy falls. This is the same observation that motivates context-dependent over isolated-word correction in the classical literature [kukich1992techniques] and that drives neural re-ranking in modern grammatical error correction [omelianchuk2020gector; awasthi2019pie]; adding such a re-ranker is the clearest path to closing the drop/sub gap.

## Qualitative Examples

The flagship behaviour is the recovery of ka2ru-corrupted Kazakh that superficially resembles Russian. The input «Бул маселе оте манызды болып тур», in which every Kazakh-specific letter has been replaced by its Russian look-alike, is first routed to the Kazakh path by the russified-lexicon signal (Section 5) and then restored to «Бұл мәселе өте маңызды болып тұр». Every edit here is a ka2ru inverse substitution (у→ұ, а→ә, е→ә, о→ө, ы→ы with ң restored), exactly the low-entropy regime in which the corrector excels.

Two further cases consistent with the error model illustrate the force-correct path and the drop/sub difficulty. In the force-correct case the detector flags a word that is itself a valid lexicon entry but wrong in context — for example «казак» is re-corrected to «қазақ» because the candidate's frequency dominates the flagged form; the corrector edits a lexicon-valid word only when a higher-frequency ka2ru-inverse candidate exists, guarding against gratuitous changes. By contrast, a deletion such as «мектп» (a dropped «е» from «мектеп») is recovered because only one frequent lexicon form lies within the edit radius, whereas an ambiguous deletion — where several short, frequent forms are equidistant from the corrupted token — is where the 62.0% drop rate originates: with no context model, the frequency tie-break cannot reliably choose the intended reconstruction. In all underdetermined cases the safe failure mode is to leave the token unchanged rather than emit a confidently wrong form.

## Efficiency and Deployment

The system is designed for CPU-only serving. The corrector processes approximately 3 ms per word, and a warm end-to-end request completes in roughly 9 ms; combined with single-threaded inference (`torch.set_num_threads(1)`) and a startup model warm-up, this yields a sustained throughput on the order of 200 requests per second on the test machine, which we treat as the CPU throughput ceiling for the current configuration. A single worker sustains roughly 150–193 req/s, and four workers approach the same ~200 req/s ceiling at a lower median latency (p50 $\approx$ 85 ms). The deployed Docker container (image `turan-serve`, linux/arm64, torch 2.12.1+cpu) occupies approximately 373 MB of resident memory at runtime, and the fine-tuned detector checkpoint is 316 MiB (331.5 MB) of safetensors weights. The system was validated in an accepted live pilot running in this container.

These characteristics make the system deployable on commodity hardware without a GPU; GPU execution and request batching would be required to scale substantially beyond ~200 req/s. The combination of a compact encoder, a frequency-indexed lexicon, and a deterministic rule/edit-distance corrector keeps the memory footprint and per-request latency low enough for interactive use, while the modular two-stage design leaves an explicit insertion point — contextual candidate re-ranking — for the accuracy improvements identified above.
