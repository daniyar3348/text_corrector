## EXPERIMENTAL SETUP

### Training configuration

The error-detection stage is obtained by fine-tuning the pretrained KazRoBERTa encoder (`kz-transformers/kaz-roberta-conversational`) [kztransformers2023kazroberta; sagyndyk2025kazroberta] for token classification with a two-label head ($\textsf{KEEP}=0$, $\textsf{ERROR}=1$), instantiated through the `AutoModelForTokenClassification` interface. KazRoBERTa follows the RoBERTa pretraining recipe [liu2019roberta] over the Transformer encoder [vaswani2017attention; devlin2019bert] and uses a byte-level BPE vocabulary [sennrich2016bpe]. The final model reported in this paper was trained in a Colab GPU notebook; a separate local script exists only for smoke testing and is not used for the reported results.

All hyperparameters below are taken from the final-run configuration. The encoder was fine-tuned with the AdamW optimizer (the HuggingFace `Trainer` default; no optimizer name is set explicitly), a peak learning rate of $2\times10^{-5}$, and weight decay of $0.01$. The per-device training and evaluation batch sizes were $64$ and $128$, respectively, and input sequences were truncated to a maximum length of $128$ tokens. Training ran for $2$ epochs, corresponding to $80{,}182$ optimization steps over the $2{,}565{,}771$-pair training split. No learning-rate warmup was configured (default $\text{warmup\_ratio}=0.0$) and the learning rate followed the default linear decay schedule. Mixed-precision training was enabled in 16-bit floating point (`fp16=True`; not bf16). The random seed was the framework default ($42$). Evaluation and checkpointing were performed once per epoch, with the best checkpoint (by ERROR-class $F_1$) restored at the end of training. Gradient accumulation, gradient clipping, the scheduler type, and dropout were left at their framework defaults. The training hardware was a single Colab NVIDIA T4 GPU, and the resulting fine-tuned checkpoint is $316.1$ MiB ($331{,}459{,}608$ bytes) in `safetensors` format. Per-token ERROR labels were derived by whitespace word alignment of the corrupted and reference sentences, labelling only the first sub-word of each word and assigning the ignore index ($-100$) to continuation sub-words and special tokens; the ERROR-token fraction in training is approximately $10.7\%$ [TODO: verify].

### Evaluation protocol

We evaluate at two levels of granularity on the held-out test split, which provides $25{,}000$ pairs disjoint from the training and validation splits. Token-level and end-to-end measurements are reported on a fixed $8{,}000$-sentence subset of this test split, as noted below.

At the **token level**, the detector is assessed as a binary classifier and we report precision, recall, and $F_1$ on the positive (ERROR) class, where a token counts as correct only if its predicted KEEP/ERROR label matches the gold label.

At the **sentence level**, we report an end-to-end "fully corrected" metric: the fraction of test sentences for which the complete two-stage pipeline reproduces the reference sentence exactly (every injected error corrected and no spurious change introduced). This stricter criterion penalizes both missed corrections and over-corrections, and is the primary measure of practical system utility. As an internal diagnostic of the correction stage in isolation, we additionally report, under the oracle-detection condition described below, the proportion of erroneous words successfully corrected and the precision of the changes the corrector applies, broken down by error type (ka2ru, vowel-harmony, duplication, swap, substitution, deletion). All test errors are synthetically injected by the data-generation procedure, which approximates but does not equal the distribution of human-typed errors; the system has not yet been evaluated against a gold human-annotated test set (see the limitations discussion).

### Baselines

We compare the trained pipeline against two reference points that bound the achievable range.

The first is a **heuristic out-of-lexicon detector**: a non-learned baseline that flags a word as erroneous if and only if its surface form is absent from the Kazakh lexicon. Requiring no training, it isolates the contribution of the learned KazRoBERTa detector over a simple dictionary-lookup strategy and is evaluated under the same protocols as the trained system.

The second is an **oracle upper bound** corresponding to perfect detection. Here the corrector receives gold error positions (detection $F_1=100\%$ by construction), so the sentence-level result reflects the ceiling imposed by the correction stage alone, independent of detector errors. Comparing the trained pipeline against this ceiling isolates the residual gap attributable to the corrector. The per-error-type corrector statistics above are reported under this oracle-detection condition.

### Implementation and serving environment

The system is implemented as a FastAPI service running in the project's dedicated machine-learning environment (Python 3.13 with PyTorch 2.12). For latency-sensitive serving, the correction endpoints execute synchronously in the server thread pool, intra-op parallelism is constrained with `torch.set_num_threads(1)`, and the model is warmed up at process startup to avoid first-request initialization cost. The corrector relies on a frequency-weighted lexicon of $339{,}717$ surface forms ($174{,}100$ retained as valid at frequency $\geq 2$) and a `rapidfuzz`-backed Optimal String Alignment search (restricted Damerau–Levenshtein distance with unit transposition cost) [levenshtein1966binary; damerau1964technique], guarded by a rule-based morphological analyzer. The service is packaged as a $2.84$ GB `linux/arm64` Docker image (`torch==2.12.1+cpu`); a running container occupies approximately $373$ MB of RAM. On the CPU-only test host the warm per-request latency is approximately $9$ ms, and a single worker sustains on the order of $150$–$193$ requests/s, with throughput plateauing near $200$ requests/s under multi-worker configurations.
