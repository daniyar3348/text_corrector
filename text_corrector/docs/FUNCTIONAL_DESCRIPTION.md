**Документ для:** руководителя проекта, методиста, интегратора (ИТ-специалиста заказчика).
**Назначение документа:** дать целостное представление о том, что система делает, насколько качественно, где её применять и как подключить через API.
**Дата:** 2026-06-20. **Статус продукта:** пилот принят, метрики зафиксированы.

## 1. Назначение и область применения

**Turan Text Corrector** — автоматический корректор орфографии **казахского** текста. Система получает на вход предложение или абзац на казахском языке, находит в нём орфографические ошибки и возвращает исправленный текст вместе с перечнем внесённых правок.

Главная решаемая задача — массовое исправление наиболее частотного и болезненного для казахского языка класса ошибок: **подмены казахских специальных букв русскими «двойниками»** (қ→к, ә→а, ң→н, ұ/ү→у и т. д.) и **нарушений сингармонизма**. Такие ошибки возникают при наборе на русской раскладке, при копировании из плохо оцифрованных источников, в пользовательском вводе и в наследуемых документах.

**Область применения:**
- образование (проверка письменных работ, учебные материалы, диктанты);
- государственные органы (делопроизводство, нормализация казахского текста в документах и формах);
- СМИ и издательства (предредактура, нормализация лент новостей и пользовательских комментариев);
- любые информационные системы, где требуется привести казахский текст к корректному написанию перед публикацией или хранением.

**Важное ограничение по языку.** Продукт ориентирован **исключительно на казахский язык**. Русский путь реализован как «прозрачный» (no-op): обученной русской модели нет, поэтому русский текст возвращается без содержательных правок. Подавать на исправление русские тексты не следует (см. раздел 6 и 7).

## 2. Функциональные возможности: что именно исправляется

Система обучена на модели ошибок, отражающей реальные искажения казахского текста. Ниже — типы исправляемых ошибок с примерами и приблизительной долей/качеством (по результатам оценки на отложенной выборке).

### 2.1. Подмена спецбукв на русские двойники (ka2ru) — доминирующий тип, ~31 % ошибок
Самый частый и самый «вредный» класс: казахская буква заменена на визуально похожую русскую.

| Было (искажено) | Стало (исправлено) | Что заменено |
|---|---|---|
| казак | қазақ | к → қ |
| мангызды | маңызды | н → ң |
| мателе / маселе | мәселе | а → ә |
| тур | тұр | у → ұ |

Пары, которые система обращает: қ↔к, ғ↔г, ң↔н, ә↔а, ө↔о, ұ/ү↔у, і↔и, һ↔х, ы↔і.
Качество на этом типе при идеальной детекции — около **97–98 %**.

**Пример целого предложения:**
`Бул маселе оте манызды болып тур` → `Бұл мәселе өте маңызды болып тұр`.

### 2.2. Нарушение сингармонизма (harmony) — ~98 % при детекции
Гласная в слове/суффиксе не соответствует гармоническому ряду основы (передний/задний). Система подбирает форму, согласованную по сингармонизму и присутствующую в лексиконе.

### 2.3. Удвоение символа (dup) — ~93 %
Случайно удвоенная буква. Пример: `кiтаппп` → `кітап`.

### 2.4. Перестановка соседних символов (swap) — ~83 %
Две соседние буквы поменялись местами. Пример: `мектпе` → `мектеп`.

### 2.5. Близкая замена буквы (sub) — ~70 %
Буква заменена на другую, не образующую «двойниковую» пару. Чинится слабее — кандидат неоднозначен без контекста.

### 2.6. Пропуск буквы (drop) — ~62 %
Пропущен один символ. Самый трудный класс: восстановление неоднозначно без понимания контекста.

> Доли и проценты выше — это качество **корректора** при условии, что ошибочное слово уже найдено (oracle-детекция). Итоговое (сквозное) качество системы зависит ещё и от детектора — см. раздел 5.

**Что система сохраняет без искажений:** пунктуацию вокруг слова, дефисные части, заглавные буквы (регистр восстанавливается), а также корректные слова — переисправления валидного текста не происходит.

## 3. Архитектура и принцип работы

Система построена по принципу **«языковой роутер → детектор ошибок → корректор»**. Это сознательное разделение ответственности: каждый блок решает одну задачу и проверяется отдельно.

```
                    ┌──────────────────────────┐
   входной текст →  │  1. ЯЗЫКОВОЙ РОУТЕР        │
                    │  (language_detection.py)  │
                    └───────────┬──────────────┘
                       казахский │ русский → текст возвращается без правок (no-op)
                                 ▼
                    ┌──────────────────────────┐
                    │  2. ДЕТЕКТОР ОШИБОК       │   KazRoBERTa, token-classification
                    │  размечает токены         │   метки: KEEP / ERROR
                    │  KEEP / ERROR             │
                    └───────────┬──────────────┘
                      позиции ошибочных слов
                                 ▼
                    ┌──────────────────────────┐
                    │  3. КОРРЕКТОР             │   kazakh_corrector.py
                    │  чинит помеченные слова   │   инверсные правила ru↔kk
                    │                           │   + лексикон 174k + OSA edit-distance
                    └───────────┬──────────────┘
                                 ▼
                          исправленный текст + список правок
```

### Блок 1. Языковой роутер (`language_detection.py`)
Определяет язык входа (казахский / русский / смешанный / неизвестно) по слоистой стратегии:
- наличие казахских спецбукв — сильный сигнал казахского;
- совпадение со списками частотных слов обоих языков;
- **покрытие казахским лексиконом после «руссификации»** — ключевой сигнал, распознающий казахский текст, в котором спецбуквы уже стёрты ka2ru-ошибками (поверхность выглядит «русской»). Без этого сигнала именно те предложения, ради которых система и создана, ошибочно уходили бы в русский путь.

Только казахский текст направляется в детектор и корректор. Русский — возвращается как есть.

### Блок 2. Детектор ошибок (KazRoBERTa, token-classification)
Дообученная нейросетевая модель на базе `kz-transformers/kaz-roberta-conversational` (энкодер, 6 слоёв / 12 голов / hidden 768, byte-BPE словарь 52 000). Дообучена под задачу разметки токенов на два класса: `0 = KEEP` (слово верно) и `1 = ERROR` (слово нужно чинить). Модель только **находит** ошибки — она не генерирует исправления. Это делает её работу быстрой и предсказуемой и стыкуется с правиловым корректором.

### Блок 3. Корректор (`kazakh_corrector.py`)
Для каждого слова, помеченного детектором как ошибочное, подбирает правильную форму в два хода:
1. **Инверсные подстановки** (высокая точность) — точечно обращает «двойников» и нарушения сингармонизма (к→қ, н→ң, а→ә, у→ұ/ү …). Принимаются только те варианты, которые есть в лексиконе (174 100 валидных словоформ, частота ≥2).
2. **Edit-distance fallback** (OSA-расстояние, перестановка = 1 операция) — для swap/drop/dup/sub находит ближайшую форму из лексикона.

Ранжирование: сначала валидные инверсные кандидаты (по частоте), затем — ближайший по расстоянию (тай-брейк по частоте). Пунктуация и дефисные части сохраняются: правится только кириллическая подстрока слова.

### Морфологический модуль (`services/morphology/`) — вспомогательная защита от переисправления
Казахский — агглютинативный язык: тысячи словоформ образуются присоединением суффиксов (число → принадлежность → падеж). Перечислить их все в лексиконе невозможно. Морфологический анализатор разбирает словоформу на основу и грамматические суффиксы (например, `мектептердің` = «мектеп» + множественное число + ілік септік) с проверкой сингармонизма. Это позволяет распознать валидную падежную/притяжательную форму и **не «чинить» правильное слово**, которого нет в лексиконе как готовой словоформы. Модуль также умеет генерировать корректный аллофон суффикса (правила сандхи и гармонии).

### Доступ к системе: HTTP API (FastAPI)
Вся функциональность доступна через REST-эндпоинты:

| Метод и путь | Назначение |
|---|---|
| `POST /correct-text` | основной эндпоинт исправления |
| `POST /correct-file` | исправление загруженного документа целиком (`.txt`, `.md`, `.csv`, `.tsv`, `.log`, `.docx`, `.pdf`, до 5 МБ) |
| `POST /detect-language` | определение языка без исправления |
| `GET /health` | статус сервиса и загруженной модели |

**Запрос на исправление:**
```json
POST /correct-text
{ "text": "Бул маселе оте манызды болып тур" }
```
**Ответ:**
```json
{
  "original_text":    "Бул маселе оте манызды болып тур",
  "corrected_text":   "Бұл мәселе өте маңызды болып тұр",
  "detected_language":"Kazakh",
  "confidence":       0.95,
  "corrections": [
    {
      "before":   "Бул маселе оте манызды болып тур",
      "after":    "Бұл мәселе өте маңызды болып тұр",
      "type":     "model_correction",
      "position": null
    }
  ],
  "processing_time_ms": 9,
  "status":           "success"
}
```
> При загруженной нейросетевой модели `corrections` содержит **ровно один элемент** с правкой всего текста целиком (`type = "model_correction"`, `position = null`) — это не пословный список. Пословные типизированные правки (с `type` вроде `spelling` и т. п.) относятся только к словарной заглушке (PlaceholderModel) и к планам развития, а не к ответу реальной модели.
`GET /health` отдаёт, в частности, `details.kazakh_model` (строка, начинается с `TransformerModel...`) и `details.kazakh_model_ready` (строка `"True"` — именно строка с заглавной `T`, а не булево `true`) — по ним интегратор проверяет, что загружена именно нейросетевая модель, а не словарная заглушка. Эти же значения проверяет healthcheck в Docker.

Есть также веб-интерфейс (React/Vite): страница коррекции и страница `/visualization` с интерактивной схемой архитектуры — удобно для демонстраций.

## 4. Принцип работы на примере

Вход: `Бул маселе оте манызды болып тур`

1. **Роутер:** спецбукв нет, но покрытие казахским лексиконом высокое → язык = казахский, текст идёт дальше.
2. **Детектор:** размечает токены. `Бул`, `маселе`, `оте`, `манызды`, `тур` → ERROR; `болып` → KEEP.
3. **Корректор:** для каждого помеченного слова применяет инверсные подстановки и сверяется с лексиконом: `Бул→Бұл`, `маселе→мәселе`, `оте→өте`, `манызды→маңызды`, `тур→тұр`. `болып` не трогает.
4. **Результат:** `Бұл мәселе өте маңызды болып тұр`.

## 5. Показатели качества и что они значат

Оценка проведена на отложенной тестовой выборке из **8000 примеров** (без пересечения с обучающими данными).

| Показатель | Значение | Что означает |
|---|---|---|
| **Детекция ошибок (KazRoBERTa), F1** | **97.3 %** (точность 97.1 / полнота 97.4) | насколько надёжно система **находит** ошибочные слова. Практически потолок: детекция фактически решена. |
| **Сквозная коррекция (предложений исправлено полностью)** | **80.5 %** | доля предложений, в которых после обработки **не осталось ни одной ошибки** — самый честный, «как у пользователя» показатель. |
| **Корректор при идеальной детекции (oracle)** | 88 % слов, точность изменений 91.6 % | потолок самого корректора: если бы детектор был идеален, столько слов чинилось бы верно. |
| **Baseline без нейросети** (эвристика + корректор) | F1 86.3 % / сквозь 64.6 % | для сравнения: что давала бы система без обученного детектора. Нейросеть даёт +16 п. п. по сквозной коррекции. |

**Производительность (живой сервер):**

| Сценарий | Результат |
|---|---|
| тёплый одиночный запрос | **~9 мс** |
| под нагрузкой (CPU) | **~150–200 запросов/сек** (инференс-bound) |
| потребление памяти (контейнер) | ~373 МБ RAM |

Пропускной способности ~200 req/s достаточно для пилота и большинства внутренних сценариев. Для высоких нагрузок масштабируется числом воркеров/реплик или переходом на GPU.

**Как читать цифры.** «Детекция 97.3 %» и «сквозь 80.5 %» — это не противоречие: детектор почти безошибочно находит проблемные слова, но часть из них (особенно drop/sub) корректор чинит не полностью. Разрыв между 80.5 % и потолком 88 % — это именно резерв корректора на сложных типах ошибок (см. перспективы развития).

## 6. Ограничения и зона ответственности

Система проектировалась с приоритетом «безопасного отказа»: если она не уверена — она **не калечит** текст, а оставляет слово как есть.

- **OOV (слова вне лексикона)** — редкие имена собственные, неологизмы, узкоспециальная терминология, которых нет в лексиконе. Корректор их **не исправит** (но и не испортит — оставит без изменений). Это сознательный безопасный режим.
- **Короткие обрывки (1–2 слова без спецбукв)** — языковому роутеру трудно определить язык по нескольким словам; возможен ошибочный маршрут. Детектор тоже слабее на коротких фрагментах (обучался на полных предложениях). Рекомендуется подавать связные предложения.
- **Типы drop/sub чинятся слабее** (~62 % / 70 %) — восстановление пропущенной или подменённой буквы неоднозначно без контекста.
- **Русский язык = прозрачный режим (no-op).** Обученной русской модели нет. Русский текст гарантированно возвращается без изменений во всех режимах (`correct_russian()` отдаёт текст как есть); словарь к русскому не применяется, поэтому риска исказить валидный русский нет. Подавать русские тексты не следует только потому, что они не будут исправлены (русской модели нет), а не из-за угрозы их повредить.
- **Пропускная способность на CPU** ~200 req/s; пиковые нагрузки требуют масштабирования.

**Зона ответственности.** Система — инструмент **предредактуры и нормализации**, а не замена корректору-человеку в ответственных публикациях. Для официальных документов и печати результат должен проходить человеческую вычитку. Система гарантирует, что не внесёт «фантазийных» правок там, где не уверена, но не гарантирует исправления каждой ошибки (особенно OOV и сложных drop/sub).

## 7. Методика внедрения

### 7.1. Где применять — по отраслям

**Образование.**
- Пакетная проверка письменных работ и диктантов на типовые орфографические ошибки казахского.
- Нормализация учебных материалов и оцифрованных текстов перед публикацией.
- Тренажёр: показывать учащемуся обнаруженные ошибки и предлагаемые исправления (поле `corrections`).
- Рекомендация: подавать связные предложения целиком, не отдельные слова.

**Государственные органы.**
- Нормализация казахского текста в формах, заявлениях, делопроизводстве (особенно очистка ka2ru-искажений из наследуемых документов и пользовательского ввода).
- Предобработка перед загрузкой в реестры/базы — единообразное корректное написание.
- Развёртывание в закрытом контуре: модель и лексикон вшиты в Docker-образ, внешние сервисы не требуются (важно для требований к данным).

**СМИ и издательства.**
- Предредактура лент новостей, нормализация пользовательских комментариев и UGC.
- Первый проход перед редактором-человеком: снять массовый «шум» из ka2ru/harmony, чтобы редактор занимался смыслом, а не раскладкой.

### 7.2. Как интегрировать через API

1. **Развернуть сервис** (см. 7.4) и убедиться по `GET /health`, что `details.kazakh_model_ready == "True"` (строка с заглавной `T`) и `details.kazakh_model` указывает на нейросетевую модель (строка начинается с `TransformerModel`), а не на заглушку. Те же два условия проверяет Docker-healthcheck.
2. **Отправлять текст** на `POST /correct-text` с телом `{"text": "..."}`. Ограничение длины — `MAX_TEXT_LENGTH = 5000` символов на запрос.
   Для документов есть `POST /correct-file` (`multipart/form-data`, поле `file`): сервис сам читает файл, разбивает его на предложения, исправляет целиком и возвращает текст с сохранённой разметкой — разбивать на части на стороне клиента не нужно. Ограничения: `MAX_FILE_SIZE_MB = 5` МБ и `MAX_FILE_TEXT_LENGTH = 200 000` символов.
3. **Использовать ответ:** `corrected_text` — готовый результат; `corrections[]` — для подсветки правок в UI; `detected_language` и `confidence` — для логики на стороне клиента (например, не показывать правки, если язык не казахский); `processing_time_ms` — для мониторинга.
4. **(Опционально) предварительно вызвать** `POST /detect-language`, если нужно отфильтровать не-казахский ввод до отправки на исправление.

Минимальный псевдокод интеграции:
```
resp = POST /correct-text {"text": user_input}
if resp.detected_language == "Kazakh":
    show(resp.corrected_text, highlights=resp.corrections)
else:
    show(user_input)   # не казахский — не правим
```

### 7.3. Рекомендации по эксплуатации

- **Подавать связные предложения** (а не одиночные слова) — так точнее и роутинг, и детекция.
- **Фильтровать язык на входе:** если ожидается смешанный поток, отсекать русский/латиницу до отправки (или опираться на `detected_language` в ответе) — русский всё равно вернётся без изменений (no-op), так что обрабатывать его смысла нет.
- **Длинные тексты бить на части** (до 5000 символов), желательно по границам предложений.
- **Мониторинг:** следить за `GET /health` (модель должна быть `ready`) и за временем ответа. Healthcheck в контейнере намеренно падает, если модель тихо деградировала до словарной заглушки — это сигнал к разбору.
- **Масштабирование:** под нагрузку запускать несколько воркеров/реплик; потолок CPU ~200 req/s на инстанс.
- **Человеческая вычитка** обязательна для официальных/печатных материалов.

### 7.4. Варианты развёртывания

**A. Локально (без Docker), torch-окружение Python 3.13.** Из каталога `backend/`:
```bash
KAZAKH_MODEL_PATH=$PWD/models/kazakh_detector \
  ./.venv-train/bin/uvicorn app.main:app --host 127.0.0.1 --port 8010 [--workers N]
```
(Порт 8010, потому что 8000 на машине разработки занят другим приложением.)

**B. Docker (рекомендуется для пилота/прод).** Модель и лексикон **вшиты в образ** — внешних зависимостей и загрузок нет:
```bash
bash backend/scripts/deploy.sh
# либо вручную:
docker build -f backend/Dockerfile.serve -t turan-serve ./backend
BACKEND_PORT=8010 docker-compose up
```
Образ `turan-serve:latest` ~2.84 ГБ (arm64), контейнер потребляет ~373 МБ RAM. Переменная окружения внутри образа: `KAZAKH_MODEL_PATH=/app/models/kazakh_detector`. **Гейт приёмки после сборки:** в логах должна быть строка `TransformerModel (detector+corrector) loaded`, а контейнер — в статусе healthy.

**Конфигурация** (`backend/app/core/config.py`): `KAZAKH_MODEL_PATH`, `MAX_TEXT_LENGTH = 5000`, `LOG_REQUESTS`. Файл `.env` лежит в `text_corrector/.env` (не в `backend/`).

### 7.5. Что НЕ стоит подавать на вход

- **Русские тексты, особенно длинные** — обученной русской модели нет; результат всегда возвращается без изменений (гарантированный no-op, словарь к русскому не применяется). Подавать их бессмысленно: они не будут исправлены. Русский поток разумно отсекать на входе.
- **Одиночные слова и обрывки 1–2 слова без спецбукв** — ненадёжный роутинг и детекция.
- **Смешанный казахско-русский текст без предварительной фильтрации** — корректно обслуживается только казахская часть.
- **Тексты длиннее 5000 символов одним запросом** — разбивать на части.

## 8. Перспективы развития

Эти направления обсуждались и обоснованы метриками (основной резерв качества — корректор на типах drop/sub, OOV-слова и русский путь):

1. **Морфологическая валидация кандидатов через FST (apertium-kaz, генератор) для OOV.** Позволит чинить даже отсутствующие в лексиконе словоформы, если они грамматически правильны, — снимает главное ограничение корректора (OOV), сохраняя безопасный режим.
2. **Контекстное переранжирование кандидатов** (через MLM-энкодер или n-gram языковую модель). Главный рычаг для «добивания» неоднозначных типов **drop/sub** — выбор правильного кандидата по контексту предложения. Закрывает разрыв между текущими 80.5 % и потолком 88 %.
3. **Порог уверенности детектора** — настраиваемый компромисс между пропусками ошибок и ложными правками на редких словах.
4. **Полноценная русская модель.** Снимет ограничение «русский = no-op» и сделает продукт по-настоящему двуязычным RU/KK-корректором (сейчас русский путь — заглушка вне фокуса).
